# API CORS Preflight Specification

## Purpose

This specification makes Cross-Origin Resource Sharing (CORS) preflight behavior explicit, deterministic, and observable. The system SHALL expose a dedicated `OPTIONS` handler that responds to CORS preflight requests across all routes. This capability does not alter the existing CORS policy; it only guarantees that preflight requests are handled uniformly and documented.

## Requirements

### Requirement: Explicit OPTIONS Handler for CORS Preflight

The system MUST handle `OPTIONS` requests sent to any path with a CORS preflight response. The response MUST include the standard CORS preflight headers (`Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`, and `Access-Control-Max-Age` as applicable). The existing CORS policy (allowed origins, methods, headers, and credentials) MUST remain unchanged.

#### Scenario: Preflight request to an API endpoint succeeds

- GIVEN a cross-origin client needs to call `POST /api/remisiones`
- WHEN the client sends an `OPTIONS` request to `/api/remisiones` with `Origin`, `Access-Control-Request-Method: POST`, and `Access-Control-Request-Headers: content-type`
- THEN the response status is `204 No Content`
- AND the response contains `Access-Control-Allow-Origin` matching the request origin
- AND the response contains `Access-Control-Allow-Methods` including `POST`
- AND the response contains `Access-Control-Allow-Headers` including `content-type`

#### Scenario: Preflight request to a nested path succeeds

- GIVEN a cross-origin client needs to call `PATCH /api/remisiones/123`
- WHEN the client sends an `OPTIONS` request to `/api/remisiones/123`
- THEN the response status is `204 No Content` (or `200 OK`)
- AND the response contains valid CORS preflight headers consistent with the application's policy

#### Scenario: Preflight request without CORS headers is still handled

- GIVEN an `OPTIONS` request is sent to any path without an `Origin` header
- WHEN the request reaches the application
- THEN the response is still generated by the explicit handler
- AND the response does not expose sensitive internal information

### Requirement: Deterministic Preflight Behavior

The preflight response MUST be generated by the dedicated handler rather than relying on implicit middleware fallback. The behavior SHALL be identical for all paths covered by the wildcard `OPTIONS` registration.

#### Scenario: Repeated preflight requests yield identical headers

- GIVEN two identical `OPTIONS` requests to the same path with the same origin and requested method
- WHEN both requests are processed
- THEN the CORS headers in both responses are identical

#### Scenario: Preflight does not execute the target route handler

- GIVEN an `OPTIONS` request is sent to a path that also supports `GET`
- WHEN the preflight request is processed
- THEN the `GET` route handler MUST NOT be executed
- AND no side effects of the `GET` handler occur

### Requirement: Existing CORS Policy Unchanged

The explicit preflight handler MUST NOT relax, tighten, or otherwise modify the CORS policy that is already enforced by existing middleware. Allowed origins, credentials support, exposed headers, and maximum age SHALL remain the same as before this capability was introduced.

#### Scenario: Actual cross-origin GET request still follows existing policy

- GIVEN a cross-origin client sends a `GET` request with a valid `Origin` header
- WHEN the request is processed
- THEN the `Access-Control-Allow-Origin` value is exactly what the existing policy specifies
- AND the `Access-Control-Allow-Credentials` value is unchanged

#### Scenario: Disallowed origin is still rejected

- GIVEN a cross-origin client sends a request from an origin not in the allowlist
- WHEN the request is processed
- THEN the response does not contain an `Access-Control-Allow-Origin` header permitting that origin
